# Session 2 — F-T53-01 diagnosed (blocker narrowed, not yet cleared)

The blocker's stated framing — *"closes the socket with code 1000 and zero
server-side logging"* — was **partly an artefact of where the logs were read**.
Correcting that got the connection all the way to a named backend error.

## 1. The ESP server does log; `docker logs` was not the whole picture

Session 1 concluded "no server-side log line" from `docker logs tbot-ls-e2e-esp`.
The server also writes a DEBUG-level file sink at
**`/opt/tbot-esp32-server/tmp/server.log`** (`log.log_dir: tmp`,
`log.log_file: server.log`, `log_level: DEBUG`) — 9.6 MB and live-updating. Both
sinks are real; neither alone is authoritative. Anyone debugging this stack
should read the file sink, not just `docker logs`.

## 2. A connection that gets through reaches a *named* backend failure

With the connection observed end-to-end, the handshake completes normally —
`hello` received, `features: {lesson: true, renderer: teebot-lesson-renderer.v1}`
negotiated, audio rates set, differentiated config fetched — and then fails here:

```
[core.connection]-ERROR-Voice session initialization failed: 'TTS'
[DeviceToken]-WARNING-mint failed for 14:c1:9f:d1:a8:48: HTTPStatusError:
    Client error '404 Not Found' for url
    'http://backend:3000/v1/internal/devices/mint-token'
[LessonRuntime]-WARNING-lesson backend identity unavailable session_id=...
```

**Root cause of the 404 — the simulated device is provisioned in only one of the
two device registries.** `DeviceMintController.mintToken`
(`tbot-backend/src/devices/device-mint.controller.ts:79`) resolves the MAC
against the backend's **postgres** `devices` table and throws
`NotFoundException({error:'DEVICE_NOT_LINKED'})` when there is no row:

```sql
SELECT id, current_household_id FROM devices WHERE mac_address = $1
```

`seed-sim-device.sql` provisions `ai_device` + `ai_agent` in the ESP's
**manager-api MySQL** — which is what lets the ESP *accept* the socket — but
nothing was ever inserted into the backend's postgres `devices`. So the ESP
accepts the robot and the backend disowns it. Without a minted device token the
lesson runtime has no backend identity, and `assignment/current` is never
reached — which is precisely why zero lesson checkpoints were observable.

The route itself is healthy: `POST /v1/internal/devices/mint-token` returns
**401** unauthenticated from both the host (`127.0.0.1:3100`) and from inside the
ESP container (`http://backend:3000/...`), i.e. the guard runs and the path
resolves. Only the authenticated call 404s, and only on MAC lookup.

Note the next gate after that one: `current_household_id` must be non-null or the
same endpoint returns **409 `DEVICE_NOT_CLAIMED`**. The seed must both insert the
device *and* claim it to a household.

## 3. A trap that invalidates in-container debugging

`docker restart tbot-ls-e2e-esp` **reverts the container filesystem** — every
in-container source patch is lost. Session 1's `print("[[PROBE]] …")`
instrumentation and this session's were both wiped by a restart, and the probe
output that *was* observed came from a pre-restart container. Any conclusion of
the form "the probe never fired, therefore that code path is not taken" is
unsafe on this stack unless the probe is verified present **after** the restart
that is being measured (`grep -c PROBE` inside the container).

This is the most likely reason session 1 read the connection path as silent:
probes and log expectations were being compared across container generations.

## 4. What is still open

The silent-close behaviour is **not fully explained**. After a restart, three
consecutive sim runs each got a clean 1000 close with no `conn - Headers` line,
while an earlier connection in the same stack logged the full handshake. The
difference between those two states is not yet isolated — the candidates are the
supersede early-return (`core/connection.py:370`, the only truly silent return on
that path) and a stale `_active_device_connections` accept-cap (the counter
inflation noted in the T2.5 findings). Both are testable once instrumentation is
made restart-durable (bake probes into the image, or bind-mount the source).

## 6. Next blocker — voice session init fails before the hello ack

The sim client still ends with `ConnectionClosedOK`, but for a different reason
and after far more progress. The server logs, on every connection:

```
[core.connection]-ERROR-Voice session initialization failed: 'TTS'
```

A `KeyError: 'TTS'` — the sim config declares no `TTS` module, and
`create_voice_session_provider` requires one even on the `google_live` path. The
connection is torn down before the client's `hello` ack, which is what the client
reports as a clean close. This is a **sim-config completeness** problem, not a
product defect, and is the next thing to fix.
