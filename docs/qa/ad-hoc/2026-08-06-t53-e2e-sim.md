**F-T53-15 — the residual cause, and it subsumes F-T53-11.** The verifier walks a monotonic
cursor over the *concatenated* log files, not a time-merged timeline. Its result therefore
depends on the order the files are passed. On one identical capture:

```
--log-file esp,serial  -> 76/101
--log-file serial,esp  -> 73/101
```

So server-side and device-side evidence are compared in **file order, not event order**, and any
checkpoint whose evidence sits in the other file after the cursor has moved is unreachable. This
is not "pull-on-connect happens too early" as F-T53-11 framed it — the two streams are simply
never interleaved. `lesson_e2e_live_capture.py` already produces a merged `timeline.log` for
exactly this reason; the verifier should require it (or merge internally).

Blocking sub-problem for T5.3 specifically: the simulator's serial log carries firmware-style
tick timestamps, not wall-clock, so it cannot yet be time-merged with the server log. The
simulator needs to emit wall-clock alongside ticks before a correct timeline can be built.

## Session 6 — root cause of the ordered-checkpoint failures established

Built the missing half of the timeline: the simulator now emits wall-clock alongside firmware
ticks (`--timeline-log`) and `merge_timeline.py` interleaves it with the server log. Result:

```
esp,serial concatenated   -> 76/101
serial,esp concatenated   -> 73/101
merged timeline           -> 77/101   <- and a DIFFERENT set of checkpoints fails
```

`lesson_started` / `preload_ready` / `manifest_fetched` / `assignment_current` started passing,
while `lesson_prepare_sent` / `lesson_start_sent` / `lesson_step_sent` started failing. Merging
did not converge the result — it reshuffled it.

**Why: the logs cannot express event order.** The ESP log format is `YYYY-MM-DD HH:MM:SS`, i.e.
**one-second resolution**. Measured on one capture:

```
111 server lines  ->  6 distinct timestamps
busiest second    ->  51 lines
```

Fifty-one events inside a single second have no defined relative order, so no merge — however
careful — can reconstruct the true sequence. The verifier's monotonic cursor is being fed an
essentially arbitrary ordering, and the checkpoints that pass or fail are decided by tie-break
luck. **This is not a simulation artifact: live captures have the same format and the same
ceiling**, which is a standing blocker on the T5.4 gate as well.

Two ways out, both outside T5.3's remit:
1. Give the ESP log (and any serial capture) sub-second timestamps; or
2. Drop the ordered-cursor design in favour of explicit correlation — the `lesson_*` frames
   already carry a monotonic `sequence`, which is a far stronger ordering signal than log
   position and is immune to timestamp resolution entirely.

Option 2 is the more robust of the two and needs no format change.

## 1. The ESP server does log; `docker logs` was not the whole picture

Session 1 concluded "no server-side log line" from `docker logs tbot-ls-e2e-esp`.
The server also writes a DEBUG-level file sink at
**`/opt/tbot-esp32-server/tmp/server.log`** (`log.log_dir: tmp`,

## 2. A connection that gets through reaches a *named* backend failure

With the connection observed end-to-end, the handshake completes normally —
`hello` received, `features: {lesson: true, renderer: teebot-lesson-renderer.v1}`

```
[core.connection]-ERROR-Voice session initialization failed: 'TTS'
[DeviceToken]-WARNING-mint failed for 14:c1:9f:d1:a8:48: HTTPStatusError:
    Client error '404 Not Found' for url
    'http://backend:3000/v1/internal/devices/mint-token'
[LessonRuntime]-WARNING-lesson backend identity unavailable session_id=...
```

**Root cause of the 404 — the simulated device is provisioned in only one of the
two device registries.** `DeviceMintController.mintToken`
(`tbot-backend/src/devices/device-mint.controller.ts:79`) resolves the MAC
against the backend's **postgres** `devices` table and throws
`NotFoundException({error:'DEVICE_NOT_LINKED'})` when there is no row:

```sql
SELECT id, current_household_id FROM devices WHERE mac_address = $1
```

`seed-sim-device.sql` provisions `ai_device` + `ai_agent` in the ESP's
**manager-api MySQL** — which is what lets the ESP *accept* the socket — but
nothing was ever inserted into the backend's postgres `devices`. So the ESP
accepts the robot and the backend disowns it. Without a minted device token the
lesson runtime has no backend identity, and `assignment/current` is never
reached — which is precisely why zero lesson checkpoints were observable.

The route itself is healthy: `POST /v1/internal/devices/mint-token` returns
**401** unauthenticated from both the host (`127.0.0.1:3100`) and from inside the
ESP container (`http://backend:3000/...`), i.e. the guard runs and the path
resolves. Only the authenticated call 404s, and only on MAC lookup.

Note the next gate after that one: `current_household_id` must be non-null or the
same endpoint returns **409 `DEVICE_NOT_CLAIMED`**. The seed must both insert the
device *and* claim it to a household.

## Session 9 — the inbound `lesson_progress` contract, read from the source

`LessonRuntime._on_lesson_progress_impl` (runtime.py:2959) rejects a device progress frame
through five guards, in order. Any simulator that synthesises this frame must satisfy all of
them — my session-8 attempt satisfied none of the interesting ones.

1. **Runtime must be active and non-terminal** — returns immediately in FAILED/PAUSED/COMPLETED.
2. **Identity must match** (`_matches_runtime_identity`).
3. **`_accept_inbound(sequence)` — strict monotonic F→S envelope sequence.**
   `seq == last+1` → ok; `seq <= last` → duplicate no-op; **`seq > last+1` → emits
   `PROTOCOL_SEQUENCE_ERROR` and HOLDS the runtime.** The device's acks and any progress frame
   share ONE sequence stream, so injecting a frame anywhere in that stream is not free.
4. **Conversational steps ignore firmware progress entirely** —
   `"firmware progress ignored for conversational step"`.
5. **An interactive `step_completed` is ignored until the child has answered** —
   `_interactive_progress_has_response(body)` must be true.

Guard 5 is the one that matters most, and it explicitly rejects what I sent
(`runtime.py:4092-4098`):

```python
# Current ESP firmware emits result="success" with empty detail as a
# renderer placeholder immediately after drawing the step. That is not
# evidence that a child answered the prompt.
return bool(normalized and normalized not in {"success", "ok", "done", "completed", "rendered"})
```

My frame was exactly `{"event": "step_completed", "result": "success"}` with **no `detail`** —
the literal placeholder shape the runtime is written to disregard. Real evidence has to ride in
`body.detail` under one of `CHILD_RESPONSE_DETAIL_KEYS`, and must not carry a negative-response
flag or an invalid confidence.

**So the session-8 frame could never have counted as progress**, while still consuming a
sequence number and passing through the inbound path — which is the likely mechanism behind the
seven flow checkpoints that broke.

### What a correct implementation requires

* Populate `body.detail` with an observable child response (per `CHILD_RESPONSE_DETAIL_KEYS`),
  not `result="success"`.
* Keep the F→S sequence contiguous across acks AND progress frames; a gap holds the runtime.
* Do not send it for a conversational step — it is discarded by guard 4.
* Send it only after the child response is actually registered, or guard 5 discards it.

This is a genuinely different frame from the one I synthesised, and it is worth doing properly:
`lesson_progress`, `lesson_progress_posted` and `lesson_backend_progress_ordered` all depend on
robot-side progress evidence existing.

## 1. The measurement was wrong, and fixing it was not "loosening the gate"

`lesson_e2e_log_verify.py` walked a cursor by LOG POSITION. That cannot order a lesson
capture, for a reason no merge can repair: the two streams are stamped by two different
clocks, and every line is written *after* the work it describes. A correctly merged
capture therefore shows the server processing an ack **before** the device has finished
logging that it sent one — causally impossible, and enough to report `preload_ready` and
`lesson_started` as missing while they sit in the file.

Evidence that this was measurement and not product behaviour: the same green run scored
**81 / 78 / 77** on identical replays.

Three changes, in order of how much each bought:

| Change | Why it is legitimate | Result |
| --- | --- | --- |
