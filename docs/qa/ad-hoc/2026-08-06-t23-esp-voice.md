## 2. Defect 1 — classic pipeline had no lesson output-queue discipline (audio overlap)

### 2.1 Repro (RED)

While a lesson owns the speaker the firmware plays lesson audio off the SD pack. On a
`classic_pipeline` connection, **any** classic TTS sentence still streamed opus frames to
the device at the same time, mixing robot chat voice over the lesson.

`sendAudioHandle.sendAudioMessage` is the single funnel every classic TTS sentence passes
through (`core/providers/tts/base.py:608` worker, `helloHandle.py:164-165`, intent
`speak_txt`). It early-returns for Google Live connections (`:25-37`) and then, on the
classic branch, had **no lesson check of any kind** — no reference to `session_mode`, to
`lesson_runtime`, or to any lesson gate. `receiveAudioHandle.startToChat` likewise routes a
child utterance straight into `handle_user_intent` → `conn.chat` during an active lesson.

Failing assertions on base (`lesson-prod/repros/t23.red.log`):

```
FAILED ClassicLessonAudioOverlapInvariantTest::test_classic_audio_blocked_while_lesson_session_mode_active
FAILED ClassicLessonAudioOverlapInvariantTest::test_classic_audio_blocked_while_lesson_runtime_is_running
FAILED ClassicLessonAudioOverlapInvariantTest::test_classic_audio_blocked_while_lesson_runtime_is_preloading
FAILED ClassicLessonAudioOverlapInvariantTest::test_blocked_sentence_does_not_leave_device_stuck_speaking
```

The Google Live half of the same test class **passed on base** — Live already enforces the
invariant upstream in `audio_bridge._should_drop_lesson_model_output` (drops
`transcript`/`audio_start`/`audio`/`audio_chunk`/`audio_end` whenever a lesson is active
unless `google_live_lesson_prompt_output_allowed` marks the output as server-authored
lesson narration). That asymmetry is exactly what the task's scope warning predicts.

### 2.2 Fix

`core/handle/sendAudioHandle.py` — two helpers plus one guard, placed **after** the
existing Google Live early-return, so the branch is unreachable from a Live connection by
construction (no cross-pipeline leak):

```python
def _lesson_owns_audio_output(conn):
    if _is_lesson_session(conn):
        return True
    runtime = getattr(conn, "lesson_runtime", None)
    return str(getattr(runtime, "state", "")).upper() in {"PRELOADING", "RUNNING"}

def _lesson_blocks_classic_voice_output(conn):
    if not _lesson_owns_audio_output(conn):
        return False
    return not bool(getattr(conn, "lesson_prompt_output_allowed", False))
```

Design choices, and why:

* **Two triggers, matching the Live gate.** `session_mode == LESSON` *or* a runtime in
  `PRELOADING`/`RUNNING` — byte-for-byte the same activity definition as
  `GoogleLiveProvider._lesson_runtime_active` (`google_live.py:4789-4793`) and the bridge's
  gate, so the two pipelines can never disagree about *when* a lesson owns output.
* **Not a hard mute.** `conn.lesson_prompt_output_allowed` is the escape hatch the lesson
  layer opens for server-authored narration — the classic mirror of
  `google_live_lesson_prompt_output_allowed`. Without it the gate would be un-openable by
  any future classic lesson-prompt path.
* **Terminal runtimes do not block.** `COMPLETED` / `FAILED` / `PAUSED` / `IDLE` release the
  speaker immediately (tested), so a finished lesson never mutes ordinary conversation.
* **No stuck-speaking state.** The guard returns before `send_tts_message(conn, "start")`,
  so `client_is_speaking` is never latched by a suppressed sentence (tested).

## 3. Defect 2 — Vietnamese `đ` never folded in the in-lesson answer classifier

### 3.1 Repro (RED)

`runtime._matching_tokens` normalises with `unicodedata.normalize("NFKD", …)` and drops
combining marks. That folds tone marks, but **`đ`/`Đ` (U+0111/U+0110) has no combining-mark
decomposition** — NFKD leaves it as `đ`, and `"đ".isalnum()` is true, so it survives into the
token. Every marker phrase containing `đ` therefore matched only the fully-accented form.

Measured on base:

| Child utterance | Classified as | Should be |
|---|---|---|
| `bắt đầu bài học` | `already_in_lesson` | `already_in_lesson` ✓ |
| `bat dau bai hoc` | **`near_miss`** | `already_in_lesson` |
| `đọc lại` | `help_or_repeat` | `help_or_repeat` ✓ |
| `doc lai` | **`wrong`** | `help_or_repeat` |
| `con không làm được` | `unknown_or_frustrated` | `unknown_or_frustrated` ✓ |
| `con khong lam duoc` | **`wrong`** | `unknown_or_frustrated` |

Consequences on a live interactive step:

* `bat dau bai hoc` — **the campaign's own production trigger phrase** (plan §1 rule 6) —
  landing as `near_miss` means the `safeSpeaking` template takes the `brave_try` branch
  (`runtime.py:2958-2963`): the robot praises a lesson-restart request as a pronunciation
  attempt.
* `doc lai` / `con khong lam duoc` fall through to `wrong`, so a child asking for help or
  saying they are stuck gets the generic incorrect-answer retry instead of the repeat or
  encouragement branch.

This is the *same* defect class the Google Live provider already fixed on the **trigger**
side — `_normalize_intent_text` (`google_live.py:5047-5058`) carries an explicit
`replace("đ", "d")` with a comment naming the NFD gap. The in-lesson **answer** classifier
never got the matching treatment.

### 3.2 Fix

`core/lesson/runtime.py::_matching_tokens` — fold `đ`/`Đ` → `d` immediately after NFKD,
mirroring the provider helper. Both sides of every comparison run through `_matching_tokens`
(marker lists and child transcript alike), so the fold is symmetric and cannot make a wrong
answer look correct — locked by
`test_folding_does_not_collapse_unrelated_answers`.

> **Scope note (ground rule 1).** `core/lesson/runtime.py` is listed in **T2.1**'s file set,
> not T2.3's. It is fixed here because T2.3's *behavioural* mandate is exactly
> "listen-window turn handling (child answer → success/miss)" and its deep-dive checklist
> requires "Vietnamese diacritics/tone variants in trigger **and answers** match correctly".
> The change is 6 lines, additive, inside the child-answer classifier only. T2.1 was `TODO`
> (no active session) at the time of the edit. Cross-referenced in plan §5 so T2.1 does not
> redo it.

## 6. Findings routed out of scope (plan §5)

**F1 — classic pipeline has no ASR→lesson-runtime transcript route at all (HIGH).**
`runtime.on_child_response` is reached only from `GoogleLiveProvider`
(`google_live.py:393`, `:1539`, `:4742`) and from the internal
`lesson_nudge_handler.py:164` dev endpoint. `ClassicPipelineProvider` implements only the
five abstract methods and has neither `speak_lesson_step_prompt` nor
`open_lesson_child_response_window`; `receiveAudioHandle.startToChat` routes the child's
transcript into `handle_user_intent` → `conn.chat` with no lesson branch. Consequently, on
a `classic_pipeline` device an interactive step can **never** be answered — it always walks
the reprompt → `lesson_abandoned{child_inactive}` path. Nothing gates lesson start on voice
mode (`runtime.py` contains no `voice_mode` reference), so this configuration is reachable.
Production default is `voice_mode.type: google_live` (`config.yaml:133`), which is why it
has not bitten. **Needs a product decision** — either declare classic unsupported for
lessons and gate `lesson_prepare` on it, or wire the route — and either way it touches
`receiveAudioHandle`/`connection.py`, outside T2.3's file scope. → **T2.1**

**F2 — the S13 voice-latency rollback lever is blind on the classic pipeline (MED).**
`PreloadVoiceLatencyAlarm` is fed exclusively from `conn.note_voice_round_trip`, whose only
production caller is `audio_bridge._note_voice_round_trip` (`audio_bridge.py:1178-1186`).
A classic-pipeline device therefore records zero samples, `current_p95()` stays `None`, and
the auto-disable can never trip no matter how badly voice latency regresses during a
preload. Adding classic instrumentation is new measurement code, not a bug fix. → **T6.2**

**F4 — an S13 alarm auto-disable during an active lesson leaves the child in permanent
silence (HIGH).** `ConnectionHandler._disable_lesson_runtime` (`connection.py:2218-2257`)
flips the flag, cancels the pull task and detaches/closes the runtime, but never touches
`session_mode`; `LessonRuntime.close()` (`runtime.py:1344+`) does not release lesson mode
either. `session_mode` therefore stays `LESSON` for the rest of the connection — and every
voice output path keys off exactly that. `_should_drop_lesson_model_output` computes
`in_lesson` from `session_mode == LESSON` **or** a live runtime state, so a detached runtime
does not help: the `or` short-circuits on session mode and all Live model output is dropped.
The classic gate added in §2 mirrors it. Deliberately **not** diverged here: making classic
behave differently from Live would violate ground rule 1 and hide the shared root cause. The
fix belongs in `_disable_lesson_runtime` (release or finish lesson mode on trip);
`connection.py` is in no part of T2.3's scope and lesson-terminal session-mode semantics are
T2.1's mandate. Pre-existing on the Live path — not introduced by this session. → **T2.1**

**F5 — `AssetCachePreloadTest` is wall-clock flaky (MED).** Full diagnosis in §5.1. Any task
running the ESP suite will see spurious red here and cannot distinguish it from a real
regression; the preload deadline needs an injectable clock or a wider margin. → **T2.2**

**F3 — a TTS-provider failure mid-step produces a silent step, not a typed event (LOW).**
When `speak_lesson_step_prompt` fails, `_speak_lesson_prompt_text` logs `handoff=0` and the
step proceeds without narration; the child hears nothing and the step ends through the
inactivity path as `lesson_abandoned{child_inactive}`. The queue is not stuck (case 3
above) but the backend cannot distinguish "child was silent" from "robot never asked". A
typed prompt-failure event would need a `lesson-error-model.md` code and a backend ingest
change — cross-repo contract work. → **T5.1**
