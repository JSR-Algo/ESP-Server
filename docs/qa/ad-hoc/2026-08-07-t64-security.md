## Findings fixed here (ESP)

### F-T64-01 (HIGH) — three `/internal/lesson-runtime/*` routes skipped the auth gate

`core/http_server.py` registers these three off the server class itself rather
than through a `core/api/*_handler.py`, and they took `_request` — the argument
was unused, so there was no auth check at all, in a namespace where every sibling
route requires `X-Mint-Secret`:

```text
GET  /internal/lesson-runtime/preload-voice-alarm        -> 200 anonymously
POST /internal/lesson-runtime/preload-voice-alarm/reset  -> 200 anonymously
GET  /internal/lesson-runtime/metrics                    -> 200 anonymously
```

Live proof against the running sim ESP (`127.0.0.1:8013`) before the fix — every
other `/internal/` route answers `401 MINT_AUTH_INVALID`, these three do not:

```text
POST /internal/devices/{id}/lesson-nudge                 -> 401  MINT_AUTH_INVALID
POST /internal/devices/{id}/lesson-assets/evict-cache-key-> 401  MINT_AUTH_INVALID
POST /internal/lesson-assets/materialize                 -> 401  MINT_AUTH_INVALID
POST /internal/lesson-assets/sd-fanout                   -> 401  MINT_AUTH_INVALID
GET  /internal/lesson-assets/sd-fanout/pending           -> 401  MINT_AUTH_INVALID
GET  /internal/lesson-runtime/preload-voice-alarm        -> 200  {"alarms": 0, "connections": 0, "devices": []}
POST /internal/lesson-runtime/preload-voice-alarm/reset  -> 200  {"connections": 0, "reset": 0}
GET  /internal/lesson-runtime/metrics                    -> 200  {"alarms": 0, "connections": 0, "counters": {...}}
```

**Why HIGH, not informational.** Two reasons compound:

1. `deploy/docker-compose.prod.yml:10` publishes `"${TBOT_HTTP_PORT:-8003}:8003"`
   with **no `127.0.0.1:` bind**, so on a VPS without a host firewall the whole
   ESP HTTP surface is reachable from off-box, bypassing nginx entirely. (nginx
   itself does not proxy `/internal/`, so the compose publish is the exposure.)
2. The `reset` route is **mutating, and what it mutates is a safety control**.
   `PreloadVoiceAlarm.reset()` clears `tripped`/`last_p95_ms`/`last_disabled_at`;
   that latch is what auto-disables `LESSON_RUNTIME_ENABLED` when voice p95 during
   preload exceeds the threshold. Anonymous reset means an attacker can repeatedly
   clear the guard that takes a degraded lesson runtime out of service, and can
   erase the evidence that it ever tripped.

The two GETs additionally disclose connected device ids and full runtime counters.

**Fix.** `_authorize_internal()` on `SimpleHttpServer` delegating to the same
`LessonNudgeHandler._authorize` the other `/internal/` handlers already share
(the idiom `LessonSdMaterializeHandler` and `GenerationRetryHandler` use), applied
to all three. Fails closed: `503 MINT_SECRET_NOT_CONFIGURED` when the secret is
unset, `401 MINT_AUTH_INVALID` on a wrong one, `hmac.compare_digest` for the compare.

### F-T64-02 (MED) — the operator console published the fleet inventory anonymously, and was XSS-able

`GET /tbot/assign/` is proxied by nginx at `location /tbot/` with **no auth**
(no `auth_basic`, no `auth_request` — unlike `/nestjs/`). Two problems:

1. **Disclosure.** `_connected_devices()` pairs every live robot's **MAC** with its
   **backend device UUID** — the exact identifier `/v1/devices/{uuid}/...` takes —
   and embedded that in the page for anonymous callers. That is a fleet inventory
   handed to anyone who can reach the vhost.
2. **Stored XSS.** The inventory is interpolated into a `<script>` block via
   `json.dumps`, which escapes quotes but **not `<` or `/`**. The websocket registry
   is keyed by the device-supplied `device-id` header (`core/connection.py:395`,
   no format validation), so a robot can pick an id containing `</script>` and
   inject markup into the operator console.

**Fix.** (a) the inventory is served only to a caller proving `X-Mint-Secret`
(`_inventory_authorized`, `hmac.compare_digest`, fails closed when unset, tolerant
of a request object with no `headers`); anonymous callers still get the page with
an empty list. (b) `_script_safe_json()` escapes `<`, `>`, `&` as `\uXXXX`, which
keeps the payload a valid JSON string that round-trips to the original id while
making it inert as markup.

The page itself stays reachable on purpose: an operator loads it in a browser to
paste a parent JWT, and a browser cannot send `X-Mint-Secret`. Gating the *page*
needs a session/`auth_request` design that is deploy-side — routed to §5 as
**F-T64-05** for T7.3, with the recommendation to put `/tbot/assign/` behind the
same nginx `auth_request` already used for `/nestjs/`.

**The three POSTs were re-probed with well-formed bodies.** On the first pass they

with an explicit ownership message, while the same call against A's **own** device
answers `201`/`200`. Authorization, not validation, is the discriminator:

```text
A's token, B's device:  assignments -> 403   preload-status -> 403   lesson-events -> 403
A's token, A's device:  assignments -> 201   preload-status -> 403*  lesson-events -> 200

```

**assignmentId leg.** Assignment ids are not just path params — `lesson-events`
and `preload-status` take one in the *body*. A's token, on A's **own** device, with
**B's** assignmentId:

```text
POST /v1/devices/{A_dev}/lesson-events   body.assignmentId={B_assign} -> 403 "assignment does not belong to this device"
POST /v1/devices/{A_dev}/preload-status  body.assignmentId={B_assign} -> 403 DEVICE_FORBIDDEN
POST /v1/devices/{A_dev}/lesson-events   body.assignmentId={A_assign} -> 200 {"accepted":1}
```

B's assignment was re-read as B afterwards and showed no pollution.

**Admin leg — 44 probes, 0 reachable.** No credential, a parent JWT (privilege
escalation attempt), a wrong proxy key, and a parent JWT + wrong proxy key, each
against 11 admin lesson routes:

```text
1. no credential            -> 11× 401 UNAUTHORIZED
2. PARENT JWT               -> 11× 401 UNAUTHORIZED            (no escalation)
3. WRONG admin proxy key    -> 11× 401 ADMIN_PROXY_KEY_INVALID
4. parent JWT + wrong key   -> 11× 401 ADMIN_PROXY_KEY_INVALID
TOTAL reachable-without-admin-credential: 0
```

**Route inventory.** All 96 lesson routes carry a guard except
`GET /v1/public/lesson-assets/latest`, which is `@Public()` by design (the robot
pulls the asset index without a parent token). Posture by controller:
`AdminSessionGuard` (+`LessonRolloutGuard` on authoring/visual assets) for the 15
admin controllers, `AuthGuard` for the parent surface, `AuthGuard + RewardParentGuard`
for `/mobile/*`, `MintSecretGuard` for `/internal/lesson-asset-sync/device-result`.

Note `RewardParentGuard` only asserts *that the caller is a parent* — it does not
check the `:childId`/`:deviceId` in the path. Ownership is enforced one layer down,
in the services, which every handler feeds `req.auth.sub` + `req.auth.household_id`.
That works (proved above) but it means the guard name oversells what the guard does.

### Box 2 — asset URLs: risk-accepted in writing

**Finding.** Lesson asset URLs are **unsigned, unscoped and never expire**. There is
no signing machinery anywhere in `src/lessons/` — URLs are plain
`${LESSON_ASSET_ORIGIN_BASE}/<path>`. The ESP-side route
`GET /tbot/lesson-assets/{cacheToken}/{assetKey}` is likewise anonymous, and its
`cacheToken` is nothing but **base64url of the cache key** — not a signature. Since
the cache key is published by the anonymous `GET /v1/public/lesson-assets/latest`,
the "non-guessable" property does not hold: index → cacheKey → base64url → download.

**Accepted, because:**

1. It is **deliberate and contract-enforced**, not an oversight. The manifest
   contract specs actively *forbid* signed URLs — `direct-mp4-cinematic.contract.spec.ts:178`
   rejects the keys `signedUrl`, `auth`, `claim`, `derivativeAssetId`, `encryption`,
   and `flattened-mjpeg-cinematic.contract.spec.ts:106` does the same. Introducing
   signing is a cross-cutting change to the T5.1 sealed-manifest contract on both
   sides of the wire, owned by T5.1/T1.3 — not something T6.4 should land unilaterally.
2. The content is **shared curriculum**, byte-identical for every household. No
   child, household, or account identifier is in the index or the assets.
3. The anonymous index is not unguarded: `validatePublicGeneration` re-derives and
   compares the canonical checksum, and `assertAssetPublicUrlSafe` validates every
   asset URL against a `publicUrlBoundary()` before serving — so internal URLs
   cannot leak into the public index.
4. Path traversal through the ESP asset route is **blocked** (verified live; the
   decoded cache key is joined unsanitised but the `realpath` prefix check catches it):

   ```text
   cacheKey=../../../../etc          -> 400
   cacheKey=../../../etc             -> 400
   cacheKey=..%2f..%2fetc            -> 404
   cacheKey=a/../../../../../../etc  -> 400
   ```

**Residual risk accepted:** anyone who can reach the backend can enumerate and
download the entire curriculum asset corpus. That is a content-piracy exposure, not
a user-data exposure. If the product later treats curriculum as paid IP, this needs
signed URLs — and that is a T5.1-contract change, logged as **F-T64-06** in §5.

### Box 3 — admin proxy key

- **Not in the client bundle — proved empirically, with a positive control.** The
  key appears only in `vue.config.js`, which configures the Node-side devServer
  proxy (Vue CLI inlines only `VUE_APP_*` into client code). Scanning the actually
  served bundle in the running web container:

  ```text
  /usr/share/nginx/html: 83 .js files
  grep 'script'          -> 44 files   (positive control: grep works)
  grep <the real key>    ->  0 files   (not in any served asset)
  grep <the real key> /etc/nginx -> 1 file  (server-side injection, correct)
  ```

- **Wrong key rejected** — live, 22× `401 ADMIN_PROXY_KEY_INVALID` (cases 3 and 4
  of the admin matrix above). An empty `X-TBOT-Admin-Key` is also rejected, not
  treated as absent.
- **Rotation works** — `TBOT_ADMIN_PROXY_KEY_PREVIOUS` is accepted alongside the
  current key, and is rejected if set without a current key. 19 tests pass:

  ```text
  $ npx vitest run src/lessons/authoring/admin-proxy-key.spec.ts \
        src/lessons/authoring/admin-session.guard.proxy-key.spec.ts
  ✓ admin-session.guard.proxy-key.spec.ts (5 tests)   # incl. "accepts the temporary
  ✓ admin-proxy-key.spec.ts (14 tests)                #  previous key during rotation"
  Tests  19 passed (19)
  ```

- Implementation is sound: `timingSafeEqual`, ≥32 chars, trimmed, placeholder
  blocklist, and fail-closed (`[]` configured ⇒ every presented key rejected).
- Worth knowing: a valid proxy key mints a **`super_admin` principal with
  `canAuthorLessons: true`**. It is a full-privilege credential whose only
  protection is secrecy plus nginx's `auth_request` in front — correct by design,
  but it means key exposure is total admin compromise.

### Box 4 — injection safety

- **Format strings — safe.** `core/lesson/interaction_templates.py:81` does
  `template.format(word=...)`, but `template` is always one of ten hardcoded
  `FUN_PATTERN_PROMPTS` values selected by dict lookup **with a safe default**;
  the lesson-supplied value is substituted *into* the template, never used *as*
  one. No `str.format` injection.
- **No shell/eval sink.** No `subprocess`, `os.system`, `shell=True` or `eval` on
  lesson text anywhere in `core/lesson/`. (`redis.eval` is Lua scripting, not
  Python `eval`.)
- **Admin (Vue) — safe.** No `v-html` and no `innerHTML =` anywhere in
  `manager-web/src`; lesson text renders through auto-escaping interpolation.
- **Mobile (RN) — safe.** No `dangerouslySetInnerHTML`, no `WebView` in
  `src/features/lesson-session` or `src/features/course`; RN `<Text>` does not
  interpret markup.
- **Operator console — was NOT safe; fixed.** See F-T64-02.

### Box 6 — rate limits (live)

```text
token brute force — 25 bad logins from one IP:
  401 401 401 401 401   (bad password)
  423 423 423 423 423   (account LOCKED after 5)
  429 × 15              (rate limit; auth:login = 10/min, keyBy ip)

ingest flood — 80× POST /v1/devices/{id}/lesson-events:
  60 × 200   then   20 × 429      (devices:lesson-events = 60/min, keyBy device)

assign flood — 40× POST /v1/devices/{id}/assignments:
  40 × 201                        (no dedicated rule -> api:default 300/min, keyBy user)
```

Ingest and token brute force are properly bounded, with defence in depth on login
(lockout *and* rate limit). **Gap, accepted:** the assign endpoints have no
dedicated rule and inherit `api:default` (300/min/user). Not a vulnerability — the
route is authenticated and household-scoped — but 300 assign/min per parent is
loose for an operation that writes assignment rows. Logged as **F-T64-07**.

The 40 × 201 does **not** create 40 assignments: the endpoint reuses the active
one (`SELECT state, count(*) → ASSIGNED | 1`), matching its documented
"creates or reuses" contract. No churn.

Also noted, not a finding: `auth:login` is `keyBy: 'ip'`, so one noisy client can
consume the login budget for every user behind the same NAT. Observed directly —
the brute-force burst locked out an unrelated second account from the same IP.
Standard trade-off; recorded so it is not rediscovered as a bug.
