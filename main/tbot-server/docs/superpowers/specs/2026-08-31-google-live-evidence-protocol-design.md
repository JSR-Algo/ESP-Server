# Google Live Evidence Protocol Design

## Goal

Make Task 4 and Task 5 evidence cryptographically non-secret, server-bounded, connection-scoped, and able to prove that cancelled model output was never forwarded after replacement output began. Preserve the normal Google Live flow when no validated evidence journey is present.

## Evidence Scope

The server accepts the existing safe `evidence_journey_id` only for Google Live connections. On acceptance it creates an evidence scope containing:

- the validated journey ID;
- the server-generated per-socket `session_id` as opaque `connectionId`;
- a stable SHA-256 digest over the available device/client IDs as `peerIdentityHash`;
- a timezone-aware UTC `serverStartUtc` generated by the server;
- the initial Google Live owner as both compatibility `liveConnectionId` and explicit `initialLiveConnectionId`.

The hello ack includes this scope. No raw device ID, client ID, token, or authorization value is logged or copied into evidence artifacts.

The journey ID, server `connectionId`, and `peerIdentityHash` are immutable for the full evidence window. A validated reconnect may change only the Live owner. The provider keeps an append-only ordered `liveConnectionTransitions` ledger; each entry contains a strictly increasing reconnect `attempt`, the exact current `fromLiveConnectionId`, and a distinct `toLiveConnectionId`.

`evidence_reopen_ready` creates only a provisional `from -> to` transition. The new Live ID becomes committed current state and enters the ordered ledger only at the successful terminal point, after all replay and other fallible reconnect work completes; the matching `evidence_reconnect_succeeded` marker names and certifies that committed transition. Any terminal failure before commit retains or restores `fromLiveConnectionId`, emits the failure marker against that rolled-back owner, and discards provisional replay and interrupt-owner migration. Replay and reconnect-success markers must name the exact provisional transition; arbitrary same-journey Live-ID drift is invalid.

## Output Ownership

During a validated evidence journey only, every forwarded model audio chunk emits a scoped ownership marker with journey, connection, Live connection, and response generation. Stale-drop markers remain optional and are emitted by the provider stale guard when an event is rejected before the bridge.

The analyzer considers a barge-in healthy without a stale-drop marker. It fails if any chunk owned by the cancelled response is forwarded after the first replacement-response chunk, including late chunks after replacement has already begun.

If a hard reconnect occurs inside an interrupt, the interrupt keeps two explicit owners. `cancelledLiveConnectionId` remains the owner of the cancelled output and stale-drop checks. `replacementLiveConnectionId` starts equal to it and may migrate exactly once through a `reason=hard_interrupt` reconnect whose ready transition receives a matching successful terminal outcome before `evidence_user_interrupted`; replay, input finalization, and replacement response markers then use the new owner. A ready transition remains provisional and rolls back on failure. Correlation is released only against the committed replacement/final owner.

Buffered input replay occurs before reconnect commit. Its scoped replay marker therefore binds to the exact pending ready transition (`attempt`, `from`, `to`, and `reason`) without publishing that transition as committed. The analyzer accepts the marker provisionally and certifies it only after the matching reconnect succeeds; a missing, mismatched, or failed provisional replay cannot satisfy reconnect coverage.

## Finalization

After the replacement response finishes, Task 4 sends `evidence_finalize` with the exact hello scope. The connection validates the scope and invokes the provider's idempotent evidence cleanup path. The provider closes Live-owned resources, logs the scoped cleanup marker and pending-task count against the final accepted Live owner, and returns `initialLiveConnectionId`, `finalLiveConnectionId`, and the exact ordered transition ledger. Only after cleanup and log emission does the server send `evidence_finalized` with the unchanged hello scope, finalized Live ownership fields, and timezone-aware UTC `serverEndUtc`.

The connection independently replays the ledger from the hello initial ID. Missing, extra, reordered, duplicated, discontinuous, or fabricated transitions; immutable identity drift; final-ID mismatch; timeout; or pending resources produce an explicit failed ack and a non-releasable Task 4 artifact. Normal socket close later reuses the same idempotent cleanup path and remains harmless.

## Correlation

Task 4 records only server-issued start/end anchors, immutable hello scope, initial/final Live IDs, and the server-finalized transition ledger. The log analyzer replays transitions in log order, validates historical markers against the owner current at that point, and requires cleanup to use the final owner. The log CLI slices the exact UTC anchors. Public correlation validates both inputs as mappings and exact-matches candidate, window, journey, connection, peer hash, initial ID, final ID, and every ordered transition. Client journey labels or final-ID equality alone can never release evidence.

## Compatibility

All new ack fields, per-chunk markers, and finalize handling are gated by a validated evidence journey. Connections without one retain the current hello payload, output logging volume, provider lifecycle, and close flow.

## Tests

- clean barge-in with no stale-drop marker passes;
- provider stale guard emits the optional scoped marker;
- cancelled output forwarded after replacement begins fails;
- same journey on another connection cannot correlate;
- server UTC anchors override client clock/skew and end only after cleanup;
- missing, failed, timed-out, or ambiguous finalization fails closed;
- reconnect attempts must be strictly ordered and bind exact old/new Live owners;
- reopen-ready remains provisional; only matching reconnect success commits the new owner, while any earlier failure rolls back to the old owner and discards provisional replay or migration;
- cleanup on a non-final Live owner fails;
- Task 4 and the server report must contain the same initial ID, final ID, and transition ledger;
- public correlator returns a failed verdict for list, null, string, and scalar inputs.
